---
name: gummble-ui-research
description: Research real mobile flow references before creating or rebuilding an important CocEnglish screen, then validate all interaction states in Flutter.
---

Trigger: major screen/flow visual implementation or redesign.
Inputs: screen/SRS IDs, OS/course target, existing tokens/components.
Read: DESIGN, COMPONENT_STATES, SCREEN_INVENTORY and GUMMBLE_RESEARCH.
Procedure: inspect configured MCP entitlement; search patterns then exact app/flow; collect2–3relevant references, dates/version/platform/plan; deep-inspect selected screens; compare hierarchy, actions, microcopy and failure states; distinguish current official product facts from archived captures; map project tokens; implement fixtures; screenshot narrow/wide/text2 and review intentional differences.
Output: reference links/IDs and provenance, component/state mapping, screenshots/diff notes.
Validation: every enabled button has defined action/API/error/retry; semantics and safe areas; no invented current product rule.
Prohibited: treating Gummble as production Flutter generator, making paid MCP a runtime requirement, undocumented proprietary DESIGN.md, generic dashboard substitution, endless search when catalog gap. If MCP unavailable, use recorded references and official public design, clearly label gaps.
