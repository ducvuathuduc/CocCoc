# Data model and ownership

One serverless TablesDB database, ID cocenglish. Row/table/index APIs, not mixed DocumentsDB collection APIs. Native database relationships are unnecessary; use IDs and owner validation. Appwrite supports atomic staged row operations and conflict detection; see [transactions](https://appwrite.io/docs/products/databases/tablesdb/transactions).

Types: id=ASCII opaque string≤36 (Appwrite varchar36); timestamp=UTC ISO8601 datetime; revision=integer≥0; text has explicit maximum; JSON means validated JSON **encoded into a string column**, not an assumed native JSON column. Large content is in Storage. Every mutable row has revision, createdAt, updatedAt; these are project fields beside Appwrite system fields. Deterministic IDs are first32 hexadecimal characters of SHA-256(namespace|stableParts), with collision detection; external event/operation IDs are UUID. Appwrite IDs must satisfy platform constraints.

Implicit column types are fixed conventions, not guesses, and the declaration generator fails on any column outside them: *At/*Until=datetime; *Id/*Identity/*Version=string36; *Hash/*Sha256=string64 (hex); day/periodKey=string10 (YYYY-MM-DD or period key); *zone=string64 (IANA); locale=string16; type/operation/key/providerAlias/leaseOwner=string64; *Delta/*Seconds/*Xp/counters=integer. Explicit `≤N` sizes and `a..b`/`≥N` ranges in the table below override them. String storage is varchar≤2048, text≤16383, mediumtext above (node-appwrite 29.2.0). `appwrite/schema/foundation.json` is regenerated from this file with `pnpm schema:declare` and checked by `pnpm schema:plan`/`pnpm schema:test`; 59 canonical tables.

Every listed unique index is created and awaited before enabling writes. Composite queries use explicit indexes. No default broad client table permission; [PERMISSIONS](PERMISSIONS.md) governs every table.

## Derived, configured and client-only data (deliberately no table)

Content (course/section/unit/node structure, guidebooks, grammar tips, lexicon/word text, stories/adventure/roleplay scripts, CEFR score bands, quest/achievement/shop catalogs) lives in signed published manifests or versioned server config, not user rows. Derived on read: profile weekly XP chart, friend suggestions, Duolingo-style score band text, quest progress shown on result screens, achievement next-tier progress, league rank (sorted members), streak calendar (p_day_activity). Appwrite Auth owns email, password, phone number/verification, OAuth identities and push targets (Messaging); Progress stores none of them. Device-only: app icon, theme, home-screen streak widget style, remembered-account hint, offline journal/cache, onboarding draft before sign-up. Static: legal pages and open-source notices. Not modeled (out of V1 scope by decision): ads/rewarded-ad grants, Math/Music/Chess, Duolingo English Test, forums/discussion, promo-code catalog, data-export archive files.

No table is freely modified by another service. The database ID is shared for cost, not a shared domain model. Consumers store only validated event projections; private profile reads use Progress API. Client read access is limited to published files and own p_notifications.

## Storage bucket and content schema

Bucket learning-assets, fileSecurity enabled. File IDs deterministic hash from owner/type/content hash. Published l_ assets read public; draft assets no client permission; temporary a_ audio only AI server credential. Prefix is an app convention, not bucket-level security. No mobile upload permission; assessment audio is bounded base64 to AI, which writes privately.

LessonBundle fields are exactly OpenAPI: schemaVersion=1, course/node/lesson/version/reward identifiers, title/skills, optional guideText, typed exercises, assets, gradingRulesVersion, manifestHash, signatureKeyId and signature. Normal lesson has10 originals; generated review5–20. Exercise gradingRule holds acceptedText/choice/token/pair rules and normalization flags. fillBlank has one authored blank and a text answer in V1. Retries reuse the original immutable item. PairAnswer carries actual leftId/rightId matches; compare against authored Pair.left.id/Pair.right.id, reject duplicates/unknown IDs. Publication rejects contradictory rules, empty accepted text or missing media alternative. Alternative exercise may not itself contain alternatives, preventing recursive bundles.

Content integrity: RFC8785 JCS-canonicalize the bundle with only manifestHash and signature omitted; preserve all string codepoints and include signatureKeyId. SHA-256 of these UTF-8 bytes is manifestHash; Ed25519 signs the same bytes, encoded base64url without padding (86 chars). ## Transaction boundaries

Learning start touches active slot, session, receipt and (LIMITED mode) reads l_energy. Answer touches session revision, unique answer, receipt and l_energy; aggregate read is staged/touched so concurrent commands conflict. Completion touches session, active slot, enrollment, up to20 review items, up to10 mistakes, at most one activity-progress row, receipt and outbox (≤36 writes). Offline full replay has≤60answer writes plus those bounded rows, below Free100 operations. Published manifest pointer flip is separate from asset uploads; incomplete uploads stay unreferenced and are cleaned later.

Progress consume touches unique inbox, first-reward marker when applicable, reward ledger, aggregate, day counters, quest counters, notification and receipt; recompute streak uses paginated day reads and conditional aggregate revision. A conflict restages every dependent read/write; no stale aggregate overwrite. Caps and first-reward decision use rows written in the same transaction. League close is checkpointed at≤30-member cohort boundary, and final result is published only after all cohort rows and watermark verified.

AI reserves user daily allowance, active slot and session/job in one transaction before outbound provider call. Provably failed token mint releases reservation; ambiguous mint consumes the entire180s admission budget. Successful mint moves180s reserved→used permanently for the UTC day; closing/heartbeat does not refund it. Expiry releases active slot only. Provider token never stored in logs/database.

Profile initialization writes p_rewards plus one INITIAL ledger credit of20 gems, profile (generated username), preferences, league profile, FREE entitlement, zone history and receipt atomically.

Progress economy commands: shop purchase writes p_reward_ledger SHOP (gems), p_item_ledger, p_inventory (or p_rewards.freezeSlots via p_freeze_ledger) and receipt; an energy refill additionally writes p_outbox energy.granted.v1 for Learning. Boost activation consumes inventory and writes p_boosts. Streak repair consumes gems/item and restores currentStreak from lostStreak within the offer window. Friend-streak invite/accept, interactions (GIFT_BOOST also charges gems and grants the boost), block (deletes both follows, ends friend streak) and report are single-transaction commands with receipts. Verified store purchase writes p_purchases, p_entitlements and outbox entitlement.changed.v1 together; family/gift/referral redemptions update p_entitlements the same way. League settlement updates p_league_profiles and LEAGUE ledger gems in the cohort checkpoint. AI conversation completion writes a_conversations and a_outbox ai.practice.completed.v1; Progress credits PRACTICE XP from its inbox. Every later wallet delta also has a ledger row; totals reconcile including initialization. Deletion across more than100 rows uses paginated owner checkpoints; final private-row purge and account.purged.v1 outbox acknowledgement commit together, not a best-effort callback. Learning uses l_outbox; AI uses a_outbox.

Billing is MOCK (user decision 2026-10-12, P10-BILL-001). Purchases go to a server-side mock billing provider in Progress. It writes p_purchases rows with platform SIMULATION and moves them through the MONETIZATION state table from fixture outcomes. The mock verifier then writes p_entitlements and entitlement.changed.v1 in the same transaction, exactly as a real verifier would. No Google Play or App Store client, credential or purchase token is integrated. PLAY/APP_STORE stay in the enum only so a later reviewed task can add real stores without a migration.

Promo redemption (P10-PROMO-001) normalizes the code, looks up p_promo_codes by codeHash, and checks status, window and limit. It then writes p_promo_redemptions, increments redeemedCount, writes the reward and writes the receipt in one transaction. The unique (userId,promoId) index guarantees one redemption per user. A replay with the same Idempotency-Key returns the stored receipt. A new key for a code the user already redeemed returns 409; its error code is fixed when the OpenAPI operation is added. Unknown, expired and exhausted codes all return the same NOT_FOUND, so the response does not reveal which codes exist.

Mock ads (P10-ADS-001) are for the free tier only. Each p_ad_events write first reads p_entitlements in the same transaction and rejects SUPER/MAX. The server assigns dailyIndex as the next free slot under the cap. A REWARDED_COMPLETION commits its reward with the row, so a retried adEventId replays and never re-grants. There is no ad SDK, network call or revenue data.

Receipts store immutable small response fields plus resource/version references. Start-session receipt reconstructs its original immutable bundle rather than storing a >16KB duplicate response. REVIEW uses a private server-generated bundle snapshot≤64KB, built from due/mistake items from retained published versions; read through owner session API, never public file access. Lesson count is10; review count5–20. Placement starts before enrollment with expectedEnrollmentRevision=0, no reward/activity.
